# Agent report: item 1.2, component-restricted search (measured, dropped)

- **Date:** 2026-09-25
- **Status:** dropped by the plan's first rule and the orchestrator's
  drop condition (the median component is most of the session); nothing
  implemented, no engine glue spec needed. Script
  `agent-reports/scripts/component_bound.py`, committed on `perf-solver`
  with this report.
- **Scope:** `satassume/solver.py` (`_pick_branch`, `_search`,
  `entails`), unchanged; `Engine.ask`'s cone machinery, unchanged
- **Read this if:** you want to know why restricting the search to the
  query variable's connected component does not pay on the refine stream,
  why it cannot replace the cone rebuilds, and what the "43% of decisions
  outside the component" figure actually costs

## Measurement

`agent-reports/scripts/component_bound.py` (run with
`PYTHONPATH=.:<sympy>:tools`; it uses `tools/query_log.py`'s stage
tracking for the path split) wraps `Solver._solve` on the replay. Before
each `entails` solve it takes the root-plus-assumption assignment (the
held levels `entails` has just established, used for 4,492 of the 6,384
solves; for theory sessions, which hold nothing, an offline unit
propagation of the assumptions over the clauses, which under-propagates
and so over-estimates the component) and walks the connected component of
the query variable over an occurrence index of the problem clauses:
clauses with a true literal are skipped, only unassigned variables are
stepped through. `_pick_branch` is wrapped to attribute each decision of
the real search to inside or outside the component. Then, because the
decision share alone is misleading (below), a prototype of the restricted
search runs as an extra timed solve before the real one: decisions in
index order inside the component only (VSIDS after a conflict, skipping
non-component variables), stopping when the component is assigned; its
partial model is not kept as the witness and popped heap entries are
re-inserted, so the real solve and every answer are unchanged. The
prototype and the real solve agreed on every one of the 4,819 solves it
ran on (non-theory sessions).

Local machine, `PYTHONHASHSEED=0`, cold replay 4.22 s; 6,384 `entails`
solves, 1.10 s inside `_solve`:

| solves | n | component: median / p90 | unassigned: median / p90 | component ÷ unassigned: median / p90 | decisions outside | restricted prototype vs real solve |
|---|---:|---|---|---|---:|---|
| all | 6,384 | 54 / 131 | 69 / 152 | 0.88 / 0.98 | 43.3% | 487 vs 527 ms (7.6% less) |
| reused/first/evicted session | 4,870 | 48 / 127 | 66 / 139 | 0.90 / 0.98 | 42.2% | 332 vs 352 ms (5.5% less) |
| cone rebuild | 1,514 | 62 / 158 | 76 / 198 | 0.83 / 0.98 | 46.6% | 155 vs 175 ms (11.8% less) |
| theory sessions (offline assignment) | 1,564 | 58 / 140 | 78 / 144 | 0.96 / 0.99 | 32.1% | not run |
| unsat solves | 62 | 39 / 85 | 40 / 105 | 0.95 / 0.97 | 0 decisions | |

Solves with a component of size 2 (the query variable and one more):
254; every other component has 5 or more variables. Walk cost, Python,
occurrence index maintained incrementally: 1.51 s for the 6,384 solves,
more than all the searches together; 3,657 consecutive solves share
(solver, assumptions, stamp, root length), so a cached walk would cost at
best about half that. 225 distinct (solver, assumption set) pairs would
need the once-per-assumption-set full check.

**Why 43% of the decisions are outside a component that holds 88% of the
variables:** the variables outside the component are the isolated ones,
which nothing propagates, so each costs the search one conflict-free
decision with a saved phase, while one decision inside the component
propagates dozens of variables. Decisions are not work; the prototype
measures the work: **40 ms of the 527 ms of solve time it covers, 0.9% of
the replay, before paying for a walk that costs more than the searches.**

**Why the cone machinery stays:** inside a cone rebuild the component is
still 83% of the cone session, and in the polluted reused sessions 90%.
The session's clauses connect everything to the query variable: the
structural templates link every node to its subexpressions, and nodes of
one session share symbols, so under the root-and-assumption assignment
the clause graph is essentially one component. What the cone rebuild
removes (other queries' nodes) is connected to the query variable in the
solver's view; a factorization by connectivity cannot tell them apart.

## Decision

Dropped: the median component is 0.88 of the unassigned variables (the
orchestrator's drop condition), and the measured saving of the restricted
search is 0.9% of the replay before the walk's cost, far under 5%. No
solver change, no engine glue spec, no test change, no A/B or gate2 run
(no code change). The theory-mode variant of the fuzz that the plan tied
to this item is not needed for it; it remains the intended route for the
theory-hold half of 3.1.

## Risks for review

- The prototype ran first and cold before each real solve, which biases
  the comparison against it; even so it saved 7.6%. Its learnt clauses
  (rare: 409 solves see any conflict) stay in the solver, which does not
  change answers (CDCL is correct from any state) and was checked (0
  answers differ).
- The offline assignment for theory sessions ignores theory propagation;
  the component there is an over-estimate. Those 1,564 solves are 0.57 s
  of the 1.10 s, so a smaller true component there could matter more
  than elsewhere, but the held-level sessions (same shape of clause
  graph, exact assignment) show 0.90 and the mechanism of connection is
  the same templates.
- The script shares `tools/query_log.py`'s reading of `Engine.ask`'s
  control flow (a `_fresh_session` after a propagation stage is the
  cone); it needs the same update if that changes.
