## Measurement (what is covered)

One long-lived `Solver` per seed is driven through a weighted random mix of
operations; every answer is checked against a fresh `Solver` of the same
code built from the same clauses (the oracle never holds state between
calls). Operations and what each checks:

| operation (weight) | checks |
|---|---|
| `add_clause` (26), `add_clauses` (8), `add_internal` (8), `add_pattern` (5) | a `False` return means the formula is UNSAT for the oracle; insertions happen while levels are held (`_attach_held`) |
| `grow` (2) | `new_var`/`ensure_vars` while levels may be held |
| `implied` (19) | oracle's propagation set is a subset; every extra literal is entailed (oracle search); `None` only if the assumptions are inconsistent; no duplicates or contradictions |
| `entails` (13) | equal to the oracle's answer, `ValueError` included; half the literals are drawn from the last `implied` trail (the witness/consistency path) |
| `solve` (7) | equal to the oracle; the model satisfies clauses and assumptions; on UNSAT the `conflict()` core is a subset and is UNSAT for the oracle; assumption sets are the held set, an extension, a prefix or a fresh set (the `keep` prefix logic of `_solve`) |
| `propagate` (5), `root_trail` (4) | root conflict only if UNSAT; every root literal entailed (verified once per literal: root facts only grow) |
| after every step | `value()` sound for every fixed variable; complete against the oracle right after `propagate()` |

Assumption sets are mostly read off a model of the current formula (the
engine's sets are nearly always consistent) and re-drawn once found
inconsistent. 30% of seeds are "hard": 20 to 80 variables with a burst of
3-clauses at ratio 4.0 to 4.5 and small `_learnt_size_min` /
`_restart_first` on the live solver, so conflicts, learnt-clause deletion
and restarts happen at this size. A seed ends a few steps after its formula
becomes root-UNSAT.

Coverage counters over the 4,000-seed run (`python
tests/test_solver_incremental.py 0 4000`, split in two processes):

    seeds 4000 (1235 hard, 2070 ending root-UNSAT)
    implied answered from held levels   9,585
    solve continued from held levels    1,943
    clause insertions while held       34,368
    conflicts 93,181; learnt-clause deletions (reductions) 545
    entails: True 3,404 / False 3,343 / None 5,870 / inconsistent 4,046

`test_mix_covers_the_incremental_paths` asserts that each of these
counters (and restarts, UNSAT solves, `implied` None) is non-zero over the
default run, and `test_harness_catches_a_dropped_clause` mutates
`Solver.add_clause` to silently drop clauses added while levels are held
and asserts the harness catches it within 40 seeds (it does at the first
seeds), so "N seeds passed" is known to mean something.

## Change

`tests/test_solver_incremental.py` (new). Structure: a `Harness` holds the
live solver, the clause list, the current assumption set, the log and the
counters; operations are functions `fn(h)` registered with `@op(weight)`
into `OPS`; `run_seed(seed, ops=OPS, setup=None, hard=None, nv=None)`
drives one seed. A variant (theory mode) passes its own op list and a
`setup(solver)` hook applied to the live solver and every oracle. Every
failure raises `Mismatch` with the seed, step, a one-line reproduction
command and the operation log.

Seeds: `SOLVER_FUZZ_SEEDS` (default 500) from `SOLVER_FUZZ_SEED0` (default
0) in 6 pytest items; `python tests/test_solver_incremental.py START N`
runs by hand and prints the counters. Adding or reweighting an operation
changes the random stream, so seeds are not stable across versions of the
file (documented in the module docstring).

## Risks for review

- The oracle is the same code, fresh: a bug present in both the
  incremental paths and the plain from-scratch path is invisible here.
  `tests/test_solver.py` covers the from-scratch path against brute force.
- `test_mix_covers_the_incremental_paths` reads counters accumulated by the
  chunk tests in the same session and runs 300 seeds of its own only if
  fewer than 300 were accumulated; a partial selection (`-k`) of the chunk
  tests therefore triggers its own run rather than a spurious failure.
- The self-check test patches `Solver.add_clause` on the class through
  `monkeypatch` (restored afterwards) and depends on `_trail_lim`, a field
  a solver change is unlikely to rename.
- The hard seeds set `_learnt_size_min` and `_restart_first` on the live
  solver instance only; the oracle keeps the class defaults.

## Not yet in the mix

  hook and a `ForbidTheory` from `tests/theory_harness.py` are the
  intended route).
- The witness ring of 1.1 and component-restricted `entails` of 1.2: to be
  added as operations when those items land (a `solve` followed by
  `entails` on the same assumptions already exercises the single witness).
- `entails` on a variable beyond `nvars()` (growth inside `entails`), and
  `_reduce_db` between public calls (never called there by the engine).
