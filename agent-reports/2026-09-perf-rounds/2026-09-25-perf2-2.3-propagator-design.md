## 0. The block, and what the propagator covers

`rules.py` compiles the rule base to `RULE_INTERNAL`: 79 clauses over the
33 predicates of one node, already minimized for propagation (same models,
same unit propagation as the full rule base), in internal literals relative
to the node's base variable `b` (literal `2*b + const`). Shapes: 60 binary
(59 Horn), 16 ternary (8 Horn), 3 of size 4 (non-Horn). `Session.node()`
instantiates the block per node with `add_pattern(RULE_INTERNAL, b, NPRED)`:
79 list allocations and 158 watch-list appends per node, 647,761 clauses on
the replay, 83% of all watch-list visits, 82% of all propagated
assignments.

The propagator does unit propagation over the *same 79 clauses per node*
without materializing them: one shared occurrence table, evaluated at a
node's base. Horn-ness is irrelevant to unit propagation, so **all 79
clauses, 100% of the 647,761 inserted rule clauses, are covered**; nothing
of the rule block stays as clauses. The binary clauses (60 of 79) get a
direct implication table; the 19 longer ones an occurrence scan.

## 1. Solver side: the hook

**State** (set once per solver, `Solver.set_rule_block(pattern, npred)`,
called by `Session.__init__`):

- `_rb_imp[rel]`: for each relative internal literal `rel` (0..2*npred-1),
  the tuple of relative literals implied when `rel` becomes true, from the
  binary clauses (`(¬a ∨ b)`: `a → b` and `¬b → ¬a`; both directions are
  stored, the table is symmetric by construction), each paired with its rule
  index: `((q, idx), ...)`.
- `_rb_occ[rel]`: the tuple of indices of the longer clauses (3 and 4
  literals) containing `rel`.
- `_rb_clauses`: `RULE_INTERNAL` itself (tuples of relative literals).
- `_rb_base`: per-variable list, the base variable of the node the
  variable belongs to, or 0 if the variable is not a registered predicate
  variable (extends with `_grow`, like `_level`).
- `Solver.register_block(b)`: sets `_rb_base[b+i] = b` for `i < npred`,
  bumps `_stamp` (the propagation cache key) exactly as `add_pattern` does.
  Precondition, checked: every variable of the block is unassigned (true at
  the only call site: `Session.node()` allocates `b` and registers before
  emitting the node's cached facts); otherwise the caller falls back to
  `add_pattern`, mirroring today's slow path.

**Where it runs.** In `_propagate`, the loop takes literal `p` off the
trail and scans `watches[p ^ 1]`. The hook goes right there, before the
watch scan (so a rule conflict is found as early as a clause would have
found it):

    base = rb_base[p >> 1]
    if base:
        rel = p - 2 * base                    # p, relative to the node
        for q, idx in rb_imp[rel]:            # binary rules: p -> q
            l = q + 2 * base
            vl = val[l]
            if vl is None:   assign l at level dl, reason -(base << 7 | idx), trail.append(l)
            elif vl is False: confl = rule clause idx materialized at base; stop as a clause conflict does
        for idx in rb_occ[rel ^ 1]:            # longer rules containing the literal just falsified
            evaluate rule idx at base: satisfied -> skip; one non-false literal -> imply it
            with the same reason encoding; none -> confl as above

Then the watch scan of
`watches[p ^ 1]` proceeds unchanged for template, formula and learnt
clauses. `_tpropagate` (theory sessions) loops `_propagate` and
`_theory_sync` as now: rule implications land on the trail from
`_propagate` and are reported to LRA/EUF by the existing cursor. No change
to `theory.py`; the propagator is not a theory (no levels, no `check`), it
is part of Boolean propagation.

**Reasons without clauses.** `reason[v]` today is a clause (a list with
the implied literal at position 0) or `None`. The propagator stores a
negative int, `-(base << 7 | idx)` (79 < 128), which no clause can be.
`_analyze`, `_analyze_final` and the minimization loop in `_analyze` read
reasons through one helper, `_reason_of(v)`: an int reason is materialized
on demand as a list `[implied literal] + other literals at base` from
`_rb_clauses[idx]`. Materialization happens only in conflict analysis (462
conflicts on the replay, against 621,452 rule implications), so the common
path allocates nothing per implication beyond the trail append it does
today. A rule conflict clause is materialized once as the `confl` list
`_propagate` returns, which `_analyze` consumes as it does any clause. The
learnt-clause machinery is untouched: learnt clauses are derived by
resolution on materialized rule clauses, which are valid clauses of the
problem, so every learnt clause is the same kind of consequence it is
today. `_reduce_db`'s lock test (`reason[c[0] >> 1] is c`) is unaffected:
an int is never a learnt clause. `_is_learnt` is unaffected.

**Backtracking.** Rule implications are ordinary trail entries with a
level; `_backtrack` unassigns them like any other and needs no change. The
propagator has no state of its own beyond the tables, so there is nothing
to undo.

**Held levels and `_attach_held`.** Unchanged. `_attach_held` handles a
clause added while levels are held; the block is registered per node
before any of its variables is assigned, so at registration the held trail
is still the fixpoint (a fresh block with all variables unassigned
propagates nothing), exactly as `add_pattern`'s fast path today. The
propagation cache keys on `_stamp`, which `register_block` bumps, and on
the root length; both still describe the propagation function.

**Root facts.** An implication at level 0 is a root fact on the trail
like today's, so `root_trail()`, `value()` and `Session.writeback()` see
exactly what they see now (the fixpoint of unit propagation is unique;
only the trail order can differ, and nothing depends on it).

**Existing theories in the session.** `_theory_sync` reports the trail
from its cursor; rule implications are reported like propagated literals
are today. `_theory_imply` and `_theory_conflict` are untouched. The 64
cone builds and the theory sessions on the replay see the same
assignments in possibly a different order.

## 2. What stays as clauses

The structural templates (`add_internal`, 119,376 clauses, 12.9% of
watch visits, 235 ms insertion, 6.5%), the assumption formula and cone
clauses (`_emit`), cached facts (unit clauses), custom-predicate facts,
extension formulas, learnt and theory clauses. `RULE_FREE` (`polar`) is
mentioned by no rule and needs nothing. Nothing of the rule block stays
as clauses; there is no partial coverage to reason about.

## 3. Engine side (for the engine agent)

  `self.solver.set_rule_block(RULE_INTERNAL, NPRED)`.
- `Session.node()` (engine.py 191-194): replace
  `self.solver.add_pattern(RULE_INTERNAL, b, NPRED); self.nclauses += len(RULE_INTERNAL)`
  by `self.solver.register_block(b)`; keep the `else` branch
  (`ensure_vars`) for complete constants. `nclauses` is statistics only
  (`session_limit` compares `len(s.base)`), so the count simply drops.
- Cached facts (step 3 of `node()`) stay unit clauses through
  `_add_clauses`; they propagate through the block at once, as now.
- `compile.py` and the templates: unchanged (`_emit_pattern` is templates
  only). `rules.py`: unchanged; the tables are built by the solver from
  `RULE_INTERNAL`. `minimize_for_propagation` stays the definition of
  what the block propagates.
- `tools/query_log.py`, `refine_replay.py`, `gate2.py`: unchanged;
  `Solver.stats()["clauses"]` no longer counts the block (the 0.3 log's
  `vars` and `root_len` are unaffected).
- Extensions (`node_facts`) and custom predicates are outside the block.

## 4. Correctness and the gate

Argument: unit propagation over a fixed clause set has a unique fixpoint
and a unique set of root facts; the propagator performs unit propagation
over exactly the clauses `add_pattern` would have inserted, with the same
reasons available to conflict analysis, so `implied`, `entails`, `solve`
and `conflict()` are semantically identical (models and conflict cores
may differ in choice, not in validity; the first conflict clause found can
differ, hence learnt clauses can differ, and CDCL is correct under any).

Gate, in this order:

1. **Fuzz mode** in `tests/test_solver_incremental.py`: a `setup` hook
   that calls `set_rule_block(RULE_INTERNAL, NPRED)` on the live solver
   and an operation `register_block` that allocates `NPRED` fresh
   variables and registers them; the oracle (fresh solver) gets the same
   blocks as `add_pattern` clauses (the `clauses` list records them
   expanded), so every existing check (`implied` superset and soundness,
   `entails` equality, model validity, core validity, `value` and
   `root_trail`) compares propagator against clauses. A second variant
   registers blocks in the live solver *and* keeps some blocks as
   `add_pattern` clauses, mixing both. Theory mode: the same with a
   `ForbidTheory` attached and atoms on block variables. 4,000 seeds.
2. `tests/test_rules.py` and `tests/test_solver.py` unchanged and green;
   `tests/test_theory_hooks.py` unchanged (the order of `assert_lit` calls
   can change within a level; `check_protocol` does not depend on it).
3. The two replay gates, every answer identical: `tools/ab.py` (refine
   stream) and `tools/gate2.py`; the 0.3 log's cross-check totals.

## 5. Expected gain, cost, risks, work

Measured on this HEAD (cold pass 3.59 s): insertion of the block 358 ms
(10.0%), propagation on rule clauses 678 ms (18.9%), 28.9% combined.

- **Removed:** the insertion (10.0%) entirely: no lists, no watch
  appends, one loop of 33 stores per node. Watch maintenance for rule
  clauses (moving a clause to another watch list, the compaction `del
  ws[j:]`, the `c[0]/c[1]` swap) is gone. The per-node pointer chasing is
  replaced by shared tables that stay in cache.
- **Replaced, not removed:** the derivations. 621,452 rule implications
  still cost one `val` lookup and one trail append each; the 19 longer
  clauses still cost an evaluation per occurrence. Today a watch visit
  costs a swap, a lookup and often a scan for a new watch; the binary
  table costs one lookup per implied literal. Estimate: the binary part
  (about three quarters of the visits) at a third of today's cost, the
  longer clauses at about the same cost as today.
- **Realistic estimate: 10% (insertion) + 8 to 11% (propagation) = 18 to
  21% of the cold pass, from 3.59 s to about 2.9 s locally.** Ceiling
  28.9%. The rule bumps decisions: `ab.py` must show at least 5%; this
  clears it several times over, so the decision is about the design
  change, not the number.

Risks:

- `_propagate` is the solver's hottest loop; the hook adds one list
  lookup (`rb_base[v]`) per processed literal for every session,
  including those with few nodes. Measure the no-block path stays within
  noise (the check is one index and a truth test).
- Reason encoding as an int must be handled everywhere a reason is read:
  `_analyze` (two places), `_analyze_final`, and the fuzz must hit
  conflicts under the propagator (the hard seeds do: 93,181 conflicts in
  4,000 seeds today).
- Trail order changes can change which conflict clause is found first,
  hence learnt clauses and models; the gates compare answers, the fuzz
  compares validity. If a replay answer differed it would be a bug in one
  of the two propagations, not an accepted deviation.
- Theory sessions: `assert_lit` order within a level changes; LRA and EUF
  are order-independent by contract (`test_theory_hooks`,
  `check_protocol`), and the harness's `Recorder` will show any breach.
- `Solver.stats()["clauses"]` changes meaning for anyone reading it.

Work: solver side, `solver.py`: `set_rule_block`, `register_block`, the
hook in `_propagate` (about 25 lines), `_reason_of` and its three call
sites, `_grow` for `_rb_base`: about 90 lines. Tests: the fuzz mode and
operations (about 80 lines in `test_solver_incremental.py`), a direct test
in `test_solver.py` (block vs clauses on a few hand cases, conflicts
included, about 40 lines). Engine side: two call sites in `engine.py`
(about 6 lines). Scripts: none new; `rule_propagation_share.py` re-run
gives the after picture (its `add_pattern` tagging then sees nothing, by
design). One agent, one day including the gates; solver side first
(the fuzz makes it safe to land alone: with no `set_rule_block` call the
solver behaves as today), engine side as a two-line follow-up commit with
the A/B.
