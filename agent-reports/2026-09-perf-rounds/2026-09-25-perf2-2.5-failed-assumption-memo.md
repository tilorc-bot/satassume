- **Date:** 2026-09-25
- **Status:** done, kept (-10.2% against 3.3; -12.7% cumulative against the

- **Scope:** `satassume/engine.py` (`Engine._context_session`,

## Measurement

The 0.3 log shows 1,130 of 2,664 sessions built only to fail: the assumptions
hold a relation no theory interprets (`Q.le(x, pi)`, `Q.ge(x, -pi/2)`, ...),
so `assume_formula` raises `Uninterpreted` and the session is never stored.

I timed every `Engine._context_session` call on an unlogged cold pass on the
Pi (ad hoc wrapper, perf_counter only). The doomed builds are 1,130 calls,
from 63 distinct assumption formulas, and take:

- 0.423 s of 4.07–4.10 s on the branch with 3.3, **10.3%**;
- 0.431 s of 4.21 s on the reference, 10.2%.

The bound, minus the 63 unavoidable first builds, is about 9.7%.

## Change

`Engine._failed` maps an assumption formula to the message of the
`Uninterpreted` its session construction raised. It is valid under
`_failed_state = (extensions, extensions.version, tuple(relation_specs))`,
the same state the answer memo uses. `_context_session` works as follows:

- a live, reusable session is returned first, as before;
- otherwise, if the formula is in the memo and the state is unchanged, it
  raises `Uninterpreted(msg)` without building anything; if the state has
  changed, the memo is cleared;
- a build that raises `Uninterpreted` records the formula.

The memo holds up to 10,000 formulas and is cleared when full.

**Why the failure is deterministic for a given (assumption set, registry
state).** A fresh session runs `assume_formula(f)`: compile, discover, then
`Relations.process(atoms_of(f))`, which raises `Uninterpreted` if and only if
some relation atom of `f` has `status` False after processing. The atom's
status is set once, by `_interpret(atom)`: true if some spec's adapter
registers it. `LRAAdapter.register` and `EUFAdapter.register` accept or reject
an atom by parsing and linearising it alone (`interpret` / `parse`), never
from solver or cache state. The queue is drained before the check, so every
user atom is interpreted. So whether the build raises depends only on `f`'s
relation atoms and `relation_specs`. The extensions version is part of the
key only to be conservative.

The doomed build has no side effects later queries depend on:

- the session is dropped;
- nothing is written back to the fact cache (no `query_literal` ran);
- the only lasting effects are pure memos (LRA linearisation, relation atoms,
  templates) and `stats["sessions"]`.

**What the query gets on a memo hit.** Exactly what the doomed path produced:
the same exception class (`Uninterpreted`) with the same message, raised at
the same point in `Engine.ask` (the first thing after `stats["queries"]`).
`sympy_api._ask` catches it and returns None. Assumptions that are also
inconsistent get None, not ValueError, before and after: the consistency
check (`query_literal`) runs only after a session exists, so on this path it
never ran. The proposition-side outcomes are unchanged too, because they are
decided before the engine: a proposition out of scope, or a TRUE/FALSE one,
never reaches `_context_session`.

## Risks for review

- If an adapter ever decides interpretation from solver state (for example,
  "interpretable once some other atom is registered"), the determinism
  argument breaks. The memo key would then need that state, or the memo must
  go. Check `register` in `lra_adapter.py` and `euf_adapter.py` stays a
  function of the atom.
- `relation_specs` is compared by `tuple(...)` of spec objects (identity or
  their `__eq__`). Mutating a spec object in place would not invalidate the
  memo. The answer memo has the same property.
- `stats["sessions"]` now counts 1,067 fewer sessions on the stream (2,664 →
  about 1,597). The 0.3 log's session census shifts accordingly (see 2.1).
